# 08 — Security

> Threat model, access matrix and the concrete controls of phase 1, including the single-password login and why it deviates from the default.

## 1. Tier and plan

- **Tier:** `S1` baseline for the whole site + `S2` for the owner panel.
- **Hosting plan:** Vercel / Hobby. Ceilings that affect controls: 3 custom WAF rules, 1 hour of runtime logs. Controls moved into the application because of that ceiling: login rate limiting and lockout (§5), and the audit trail (§4, `admin_audit`).

## 2. Threat model

| Asset | Threat | Impact | Main control |
|---|---|---|---|
| Owner panel access | Password guessing (online brute force) | Attacker crosses out every date (visitors think it is full) or restores taken ones (double bookings asked for) | Generated passphrase, scrypt, per-IP + global limits |
| Owner panel access | Stolen session (lost phone, XSS) | Same as above, for the session lifetime | `HttpOnly` `__Host-` cookie, server-side sessions, rotation kills all sessions |
| Owner panel actions | Forged request from another site (CSRF) | Unwanted block/unblock | Server Actions (POST + origin check) + `SameSite=Strict` |
| Owner panel actions | Direct call to a Server Action without logging in | Unwanted block/unblock | `requireAdmin()` first line of every action |
| Credential hash | Database leak | Offline cracking | scrypt N=2^17 + a passphrase of ≥ 60 bits entropy |
| Public page | Content injection / clickjacking | Defacement, fake link | React escaping, CSP, `X-Frame-Options: DENY` |
| Visitor data | — | **Not stored.** The form never reaches the server | — |

Out of scope: denial of service at network scale (Vercel's default mitigation), compromise of Mateo's Vercel/Neon/GitHub accounts (2FA on all three is a launch checklist line, §8).

## 4. Controls

| # | Control | Specification | Check |
|---|---|---|---|
| C-01 | Passphrase | **Generated by Mateo**, never chosen by the client: 6 random words from a large wordlist or ≥ 20 random characters. Delivered in person or by voice, never written in WhatsApp | Entropy stated in the handover note |
| C-02 | Password storage | `crypto.scrypt`, N = 131072 (2^17), r = 8, p = 1, 16-byte random salt, 64-byte key, `maxmem` 256 MiB. Stored as `scrypt$N$r$p$saltB64$hashB64` in `admin_credential.password_hash`. Compared with `crypto.timingSafeEqual` | Hash row exists; plaintext absent from repo, logs and DB |
| C-03 | Session creation | On success: 32 random bytes → base64url token; store `sha256(token)` in `admin_sessions` with `credential_version` and `expires_at = now() + 30 days` (`D-008`). A new session id every login (no fixation) | Token visible only in the cookie |
| C-04 | Cookie | Name `__Host-araucaria_admin` · `HttpOnly` · `Secure` · `SameSite=Strict` · `Path=/` · no `Domain` · `Max-Age` 30 days | DevTools cookie flags |
| C-05 | `requireAdmin()` | In `lib/dal.ts`. Reads the cookie → hashes → loads the session → rejects if missing, `revoked_at` set, `expires_at` past, or `credential_version` ≠ current. **First line of every admin Server Action and of every admin page data read** | Calling an action with no cookie returns `UNAUTHORIZED`; tested by hand with a POST |
| C-06 | `proxy.ts` | Only redirects `/admin/*` (except `/admin/login`) to login when the cookie is **absent**. No DB, no decisions | File contains no access decision |
| C-07 | CSRF | Mutations only through Server Actions (POST, origin checked by Next). No route handlers that write. `serverActions.allowedOrigins` left unset | No `app/**/route.ts` with POST/PUT/DELETE |
| C-08 | Input validation | zod on every action; dates within today_AR … today_AR + 12 months; module from an enum; ids are uuids | Malformed POST returns `INVALID_INPUT` |
| C-09 | Bot filter on login | Honeypot field `website` must be empty; submissions < 2 s after render are rejected as `INVALID_CREDENTIALS` | Filling the hidden field fails |
| C-10 | Logout | Sets `revoked_at`, clears the cookie, audits. A **visible "Cerrar sesión"** in the panel topbar | Session row revoked after logout |
| C-11 | Audit | `admin_audit` rows for `login_ok`, `login_fail`, `login_locked`, `logout`, `block`, `unblock`, `password_rotated`, with `ip_hash` and session id. Kept 12 months | Rows appear for each action |
| C-12 | Errors | Generic messages to the user; details only in server logs. No stack traces in production | Forced error shows the generic copy |
| C-13 | Headers | `07-INFRASTRUCTURE.md` §Security headers; `/admin/*` also `noindex` + `no-store` | Response headers in DevTools |
| C-14 | Secrets | Only `DATABASE_URL` and `IP_HASH_SALT` are secret. Post-build grep of `.next/` for each secret value returns zero hits | Grep before launch |
| C-15 | Public read minimalism | `getAvailability()` returns only `date` and `module` | Response payload inspected |

## 5. Login order and limits

Inside `login`, in this exact order:

1. `ip = ` the client IP from Vercel's forwarding header (first address; verified in WU-03) → `ipHash = HMAC-SHA256(IP_HASH_SALT, ip)`.
2. **Per-IP limit:** failed attempts from `ipHash` in the last **15 minutes ≥ 5** → audit `login_locked` → `RATE_LIMITED`.
3. **Global limit:** failed attempts from anyone in the last **60 minutes ≥ 20** → audit `login_locked` → `RATE_LIMITED` for everyone until the window clears.
4. zod + honeypot + time trap.
5. scrypt verify.
6. Insert into `login_attempts` (`success` true/false) and audit.
7. On success: create the session, set the cookie, run the purges (`04-DATA-MODEL.md`), redirect.

| Limit | Value | Counted in |
|---|---|---|
| Per IP | 5 failures / 15 min | `login_attempts` (Neon) |
| Global | 20 failures / 60 min → login closed until the window clears | `login_attempts` (Neon) |

**Known trade-off:** an attacker can trip the global limit on purpose and keep the owner out for up to an hour. Accepted for a panel used a few times a week. Mateo can clear it by deleting recent failed rows.

## 6. Password rotation

- **When:** at handover, when anyone who knows it stops needing it, and on any suspicion. **Not** on a calendar.
- **How (operator script, run by Mateo):**
  1. Generate a new passphrase.
  2. Compute the scrypt string locally.
  3. `update admin_credential set password_hash = …, credential_version = credential_version + 1, rotated_at = now()`.
  4. Insert an audit row `password_rotated`.
- **Effect:** every existing session fails `credential_version` → all devices are logged out at once.
- The script lives in `scripts/` and never prints or logs the passphrase.

## 7. Not implemented, with reason

| Control | Why not in phase 1 |
|---|---|
| Auth from a maintained provider (`S2-01`) | Deviation chosen by Mateo (`D-007`). Compensated by C-01…C-11 |
| MFA (`S2-06`) | Same deviation. Compensated by a generated passphrase, limits, audit and one-step revocation |
| Password reset by email (`S2-05`) | There is no email identity. Reset = operator rotation (§6) |
| RLS (`S2-08`) | The DB is never exposed to the browser; one server-side role only |
| Webhook verification (`S2-09`), money integrity (`S2-10`) | No webhooks, no money in phase 1 |
| Error tracking (`S2-12`) | Deferred (`OQ-04`); Vercel logs + audit table for now |
| Per-person accountability | One shared account by decision; the audit trail records the session, not the person |

## 8. Pre-launch checklist

- [ ] C-01…C-15 each checked as written
- [ ] Login limits tested: 5 wrong passwords from one IP lock that IP; the 6th correct attempt is still refused inside the window
- [ ] A POST to `blockModules` without the cookie returns `UNAUTHORIZED`
- [ ] Rotation tested on preview: a logged-in phone is logged out after rotation
- [ ] Post-build secret grep: zero hits
- [ ] 2FA enabled on Mateo's GitHub, Vercel and Neon accounts
- [ ] `npm audit` triaged; no reachable critical/high finding
- [ ] Backup restored once into a scratch branch (`07-INFRASTRUCTURE.md`)

## 9. Reopen triggers

Move to a maintained auth provider with MFA when any of these happens: phase 2 adds Mercado Pago or online booking; more than two people need panel access; the client needs to revoke one person without affecting others; any incident involving the panel.
